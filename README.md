# PII Detection & Data Quality Validation Pipeline

## Project Overview

This project profiles, validates, cleans, and masks a customer dataset,
producing a full audit trail of every data-quality issue found and every
remediation decision made. It was built against the instructor's 4
September clarification that no external `customers_raw.csv` would be
provided — the dataset is generated by this project as a synthetic,
entirely fictitious CSV with intentionally seeded data-quality problems.

## Objectives

1. Exploratory data quality analysis (completeness, types, formats,
   uniqueness, invalid values).
2. PII detection and classification.
3. Rule-based data validation.
4. Deterministic data cleaning and normalization.
5. PII masking of the cleaned dataset.
6. End-to-end pipeline orchestration with logging and error handling.
7. Reflection and data governance documentation.

## Dataset

`data/customers_raw.csv` is generated by `src/generate_dataset.py`
(seeded with `DATASET_RANDOM_SEED` in `src/config.py` for reproducibility).
It contains 220 synthetic records following this schema:

```
customer_id, first_name, last_name, email, phone, date_of_birth,
address, income, account_status, created_date
```

About 60% of rows are fully valid. The remaining rows are each seeded
with exactly one of 22 documented error categories (4 rows per category),
so every error type is traceable and the dataset never degenerates into
unexplainable random corruption:

duplicate_customer_id, missing_email, missing_phone, missing_income,
missing_address, negative_income, income_above_10m, invalid_email_format,
malformed_phone, inconsistent_phone_formatting, invalid_date_of_birth,
non_standard_date_format, future_date_of_birth, age_above_150,
invalid_account_status, empty_first_name, name_with_invalid_characters,
name_too_long, address_too_short, inconsistent_capitalization,
inconsistent_whitespace, invalid_created_date.

All names, emails, phone numbers, and addresses are synthetic. Emails use
`example.com`/`example.org`/`example.net` domains; no real person's data
is used anywhere in this project.

Why synthetic data: it lets every intentional error be documented and
verified against the pipeline's actual output, and it avoids any real
personal data ever entering a repository or report.

## Architecture

```
customers_raw.csv
       ↓
    Profiling            → data_quality_report.txt
       ↓
 PII Detection            → pii_detection_report.txt
       ↓
   Validation             → validation_results.txt (pre-cleaning)
       ↓
    Cleaning              → cleaning_log.txt, customers_quarantined.csv
       ↓
 Re-validation            → validation_results.txt (post-cleaning, appended)
       ↓
     Masking              → masked_sample.txt
       ↓
 Output datasets          → customers_cleaned.csv, customers_masked.csv
       ↓
     Reports              → pipeline_execution_report.txt
```

For rendered flowcharts, a module dependency diagram, and a full
execution sequence diagram, see **[docs/architecture.md](docs/architecture.md)**.

### Modules

| Module | Responsibility |
|---|---|
| `src/config.py` | All paths and tunable constants; env-var overridable. |
| `src/generate_dataset.py` | Builds the synthetic dataset with a documented error inventory. |
| `src/ingestion.py` | Loads and sanity-checks the raw CSV. |
| `src/profiling.py` | Part 1 exploratory data quality analysis. |
| `src/pii_detection.py` | Part 2 PII classification and regex detection. |
| `src/validation.py` | Part 3 custom rule-based validator. |
| `src/cleaning.py` | Part 4 deterministic normalization and quarantine logic. |
| `src/masking.py` | Part 5 masking functions. |
| `src/reporting.py` | Renders every `.txt` report from real computed results. |
| `src/pipeline.py` | Part 6 end-to-end orchestration, logging, error handling. |

## Installation

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Or via Make: `make install`.

## Usage

```bash
# 1. Generate the synthetic dataset (writes data/customers_raw.csv)
python -m src.generate_dataset

# 2. Run the full pipeline
python -m src.pipeline
```

Or via Make: `make generate` then `make run`.

Outputs land in `outputs/`, `reports/`, and `logs/pipeline.log`. Paths can
be redirected via the environment variables documented in `.env.example`.

## Testing

```bash
pytest
```

Or via Make: `make test`.

38 tests cover ingestion, profiling, PII detection, validation, cleaning,
masking, and full pipeline execution (success and failure paths), using
small in-memory fixtures rather than the full dataset.

## Running with Docker

A `Dockerfile` is provided for isolated, reproducible execution without
setting up a local Python environment.

```bash
make docker-build
make docker-run     # generates data (if missing) and runs the pipeline;
                     # outputs/, reports/, logs/ are bind-mounted to the host
make docker-test     # runs pytest inside the container
```

Equivalent raw `docker` commands (if you don't have `make`):

```bash
docker build -t pii-data-quality-pipeline .
docker run --rm \
  -v "$(pwd)/outputs:/app/outputs" \
  -v "$(pwd)/reports:/app/reports" \
  -v "$(pwd)/logs:/app/logs" \
  pii-data-quality-pipeline
```

Or with Docker Compose (declarative volumes, no long `docker run` flags):

```bash
docker compose run --rm pipeline   # generate data (if missing) + run the pipeline
docker compose run --rm test       # run the test suite in the container
```

Or via Make: `make compose-run` / `make compose-test`.

The container entrypoint (`docker-entrypoint.sh`) generates
`data/customers_raw.csv` automatically on first run if it isn't already
present, then executes the full pipeline.

## Data Quality

Validation rules (implemented in `src/validation.py`, constants in
`src/config.py`):

- `customer_id`: integer, positive, unique, not null.
- `first_name` / `last_name`: non-empty, 2–50 characters, alphabetic
  (letters, spaces, hyphens, apostrophes), normalized whitespace.
- `email`: matches a structured `local@domain.tld` pattern.
- `phone`: matches one of the recognized US-style 10-digit shapes
  (`XXX-XXX-XXXX`, `(XXX) XXX-XXXX`, `XXX.XXX.XXXX`, `XXXXXXXXXX`,
  `+1-XXX-XXX-XXXX`); all are normalized to `XXX-XXX-XXXX` during cleaning.
- `date_of_birth`: valid calendar date, not in the future, implied age
  ≤ 150; normalized to `YYYY-MM-DD`.
- `address`: non-empty, 10–200 characters.
- `income`: numeric, 0 ≤ value ≤ 10,000,000.
- `account_status`: one of `active`, `inactive`, `suspended` after
  case/whitespace normalization.
- `created_date`: valid calendar date, normalized to `YYYY-MM-DD`.

**Validator choice: custom Python functions**, not Pandera / Pydantic /
Great Expectations. The dataset is a single flat table with rules that mix
per-row checks with cross-row logic (uniqueness) and derived values (age
from date of birth). Custom functions express this as clearly as a schema
library would at this scale, while making it straightforward to attach a
specific, human-readable failure reason per rule — exactly what
`validation_results.txt` and `cleaning_log.txt` need to show.

**Cleaning strategy**: automatically repairable issues (whitespace,
capitalization, a recognized phone/date shape) are reformatted in place;
everything else that would require inventing data (missing/invalid
identifiers, unparseable values, out-of-range values, disallowed
categories) causes the row to be quarantined, with the reason and affected
customer_id logged in `cleaning_log.txt` **and** the full row written to
`outputs/customers_quarantined.csv` (with a `quarantine_reason` column),
so quarantined records can actually be reviewed, not just counted.

**Performance note**: this project does not use a code profiler
(`cProfile`, `line_profiler`, etc.) -- it's a straightforward batch job
over a few hundred rows where per-line CPU profiling wouldn't add much.
What it does track is wall-clock duration per pipeline stage (ingestion,
profiling, PII detection, validation, cleaning, masking), logged and
included in `pipeline_execution_report.txt`, which is the practically
useful equivalent for a batch pipeline at this scale.

## Privacy

`src/pii_detection.py` classifies every column into direct identifier,
sensitive personal information, or quasi-identifier metadata, and detects
email/phone patterns with regex. `src/masking.py` implements the required
masking rules (names → `J***`, emails → `j***@domain`, phones →
`***-***-XXXX`, addresses → `[MASKED ADDRESS]`, DOB → `YYYY-**-**`).
Income is intentionally left unmasked in the masked output — see
`reflection.md` for the reasoning.

## Troubleshooting

- **`IngestionError: Input file not found`** — run
  `python -m src.generate_dataset` first, or point `PIPELINE_DATA_DIR` at
  a directory that already contains `customers_raw.csv`.
- **`ModuleNotFoundError: No module named 'src'`** — run commands from the
  repository root using `python -m src.pipeline`, not
  `python src/pipeline.py`, so the package import resolves correctly.
- **Tests fail after editing `src/config.py` paths** — the pipeline test
  suite monkeypatches config paths per test; if you add a new path
  constant, add it to the `isolated_pipeline_dirs` fixture in
  `tests/test_pipeline.py` too.
